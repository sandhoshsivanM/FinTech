1Summary

Two products (ADR 0007, 22 October 2026). Khazana ships as two separate apps on every platform. Khazana (offline: webapp/ and the Flutter app at the repo root) never has an account, a login, sync or calls to our servers. Khazana Online (webapp-online/ and mobile-online/) is a separate app built around an account and end-to-end encrypted sync, and is the only client of the backend. They share domain code and design tokens at build time only; data moves between them by backup file. Where this document says "the app" gains sign-in, sync or a server feature, read "Khazana Online".

Khazana v2 adds automatic data capture, and a separate online app with multi-device sync, alongside the existing offline-first app. The phone stays the source of truth, and the server is a thin, encrypted relay that never stores readable financial data.

What v2 does

  • Captures transactions automatically from bank SMS (Android), bank-app notifications (Android, already in v1), card alert emails (Gmail), receipts and screenshots (on-device OCR), and bank data through the RBI Account Aggregator (AA) framework.
  • Posts confident entries straight to the ledger with a notification and Undo. Doubtful entries go to a Review inbox where the user approves, edits the amount (for example ₹1,000 → ₹10,000) or rejects. Pending entries never change a balance.
  • Covers the whole financial picture: bank accounts, credit and debit cards, FD/RD, mutual funds, ETFs, NSE/BSE stocks, bonds, NPS, EPF/EPS/PPF, insurance, plus credit report and card-offer savings.
  • Syncs every device (Android, iOS, macOS, web) with end-to-end encryption.
  • Keeps every v1 screen and the existing theme, with smoother motion, prototyped before implementation.

2Goals, non-goals and principles

The main purpose is to cut manual data entry to near zero without giving up the privacy that defines Khazana.

Goals

  • G1 Automatic capture. Most transactions arrive with no typing.
  • G2 Online: every device. In Khazana Online, the same data on phone, laptop and web. The offline app stays local only.
  • G3 Complete net worth. Banks, cards, deposits, market investments, retirement schemes and insurance.
  • G4 Card intelligence. Credit report, card due dates, and "you can save ₹X with the cards you already have".
  • G5 Smooth UI. Existing theme with better motion and transitions.

Non-goals

  • Lending, selling cards or loans, ads, or selling user data.
  • Locking any feature that's free today. How v2 earns money is open decision D13.
  • Trading or placing orders. We show holdings, not a broker.
  • Tick-by-tick live prices. End-of-day prices are enough.
  • An account, a login or a server in the offline app. Online features live in the separate Khazana Online app (ADR 0007).

Deployment

  • Region: AWS ap-south-1 (Mumbai), keeping data in India. One ECS Fargate service per microservice (two small tasks each in production), plus the gateway.
  • Managed data services: RDS PostgreSQL (Multi-AZ in production) holding one database and one login per service — separate instances only when load demands it; Amazon MQ for RabbitMQ (or self-hosted on Fargate to save cost early); S3 with versioning; KMS and Secrets Manager. Redis only when caching needs it.
  • While building: nothing in the cloud. .NET Aspire runs every service, Postgres and RabbitMQ on the laptop with one command, at ₹0.
  • Edge: CloudFront plus WAF in front of the API, with rate limits per IP and per user.
  • Environments: dev, staging (wired to the AA and bureau sandboxes) and prod, all defined in infrastructure-as-code (Terraform or CDK).
  • CI/CD: extend the existing GitHub Actions (.github/workflows/ci.yml) with one backend job per service, triggered only by changes under its folder (build, tests, contract tests, container image, deploy to staging on merge, manual promotion to prod).
  • Web hosting: the web app keeps its static Netlify deploy. The Netlify quote function moves into the backend.

6Login, identity and encryption keys

There are two separate locks. The online account proves who you are to the server, and the existing vault PIN unlocks your data on the device. The server can never read data even with a valid login.

Sign-in methods

MethodWhenNotes
Sign in with GoogleLaunchMost Android users have it. The app verifies Google's ID token, and the backend issues our own tokens.
Sign in with AppleLaunch (iOS)Apple requires it (or an equivalent) when an iOS app offers third-party sign-in.
Email magic linkLaunchFallback for users without Google or Apple. Sent via SES.
PasskeysLaunch (preferred)Phishing-resistant, no passwords to leak. Offered first wherever the device supports it.
Phone OTPNot usedEvery SMS costs money, and SIM-swap fraud is a known attack on Indian finance apps.

Recommendation: issue tokens ourselves (verifying Google and Apple ID tokens is a small amount of code with no per-user fees) rather than using a paid identity service. Decision D3.

Tokens and sessions

  • Access token: JWT signed with ES256, valid 15 minutes, carrying sub (user), did (device) and scope.
  • Refresh token: random 256-bit, valid 30 days, rotated on every use with reuse detection (a reused token revokes the whole device session). Stored hashed on the server.
  • Storage on the client: Keychain / Keystore through flutter_secure_storage on the app. Web uses an httpOnly, Secure, SameSite=strict cookie.
  • Devices: each device is registered with a name, platform and public key. Users see their devices and can log one out remotely.
  • Device-bound tokens (DPoP): each device holds a signing key in its secure chip (Secure Enclave / StrongBox, non-exportable). Every API request carries a fresh signature with that key, and the server rejects tokens presented without it. A stolen token can't be used from any other device.
  • Step-up: sensitive actions (new device, consents, credit pull, export, deletion, bulk delete) need a fresh biometric or PIN check (§14.3).
  • Attestation: sign-in and sensitive calls include a Play Integrity or App Attest verdict, so only the genuine app gets tokens.

Flows

First sign-in (new user)

  1. User taps Google or Apple. The app receives an ID token.
  2. POST /v1/auth/token with the ID token and device info. The server verifies it, creates the user, identity and device, and returns access and refresh tokens.
  3. The app generates the DEK and device key pair, wraps the DEK to the device key and to the recovery key, and uploads both envelopes (POST /v1/keys/envelopes).
  4. The app shows the recovery key once and asks the user to confirm it was saved.
  5. The first sync push uploads existing local data, encrypted.

Adding a second device

  1. The new device signs in and registers its public key, but has no DEK yet.
  2. The user scans a QR code on the new device with an existing device, or enters the recovery key.
  3. The existing device wraps the DEK to the new device's public key and uploads the envelope. The new device unwraps it and pulls the sync history.

Account deletion

The user can delete their account from the app. All server rows and S3 objects are deleted within 30 days (backups expire on their own schedule), AA consents are revoked, and an audit event is kept without any financial values. Local data stays on the device unless the user also wipes it.

7HLD: backend

Ten small .NET services behind one gateway, each with its own database, talking to each other through RabbitMQ events. Chosen deliberately so the project teaches microservices; every service stays coarse-grained so one person can build and run them.

Why microservices (D1). The goal is hands-on microservice experience, not scale — at 10,000 users one API would cope. The cost is real and accepted: about 3–4 more months of work, more moving parts, and hosting of ₹5–12 L/yr instead of ₹3–8 L. Four things keep it manageable alone: .NET Aspire runs the whole system locally with one command; services are split by business capability, never per table; shared building blocks (messaging, outbox, crypto) are written once; and every service starts as one database on one shared RDS instance.

7.3 Cross-cutting rules

  • No shared databases. A service changes another service's data only by sending it a message or calling its API.
  • One synchronous hop at most. Gateway → service is fine; service → service → service chains are replaced by events, so one slow service can't stall a request.
  • Outbox + idempotent consumers: an event is written in the same transaction as the change it announces, and a consumer that sees a message id twice ignores the second copy.
  • Events are versioned (RecordsPushed.v1) and change only additively; a breaking change is a new version consumed side by side.
  • Correlation id on every request and message, so one trace follows a request through every service.
  • Idempotency keys on mutating POSTs; FluentValidation at every edge, unknown fields rejected; rate limits at the gateway, tighter for AA and credit calls because each costs money.
  • Time and money: UTC timestamps; money as decimal strings, never floats (same rule as v1).

8.4 Sync protocol (Sync service)

  • Record format (before encryption): {id, collection, updatedAt, deleted, data}, the shape sync_merge.dart already merges; AES-256-GCM under the DEK with record_id and collection as associated data.
  • Push: up to 500 records; the service stores them as-is, assigns seq = per-user counter + 1 and publishes RecordsPushed. It never merges — it can't read the data.
  • Pull: records with seq > cursor; the client decrypts, runs the existing last-write-wins merge and advances its cursor.
  • Conflicts: resolved on the client by updatedAt; postings are immutable once posted, so edits are new reversing and replacing postings.
  • Tombstones kept 90 days; key rotation through key_version.

How "can't see financial data" is enforced

  4. No impersonation: there is no "log in as user" feature, ever.
  5. No third-party analytics SDKs (no Firebase Analytics, Mixpanel or similar). Metrics come from server events we already have (sign-ins, token refreshes, device registrations, consent status), so nothing is shared with any outside company.

9.4 Capture lifecycle

Figure 3. Lifecycle of one captured message (as built). Only AUTO_POSTED, APPROVED and EDITED_APPROVED have an entry in the ledger. Undo removes the entry and returns the capture to PENDING_REVIEW with the reason "You undid this"; a rejected capture can be restored the same way. Decided captures are kept 90 days as the dedupe record.

9.5 Ledger rules

  • Balance = opening balance + Σ posted postings. Pending captures appear separately as "₹X waiting for review".
  • Edit and approve stores parsed_amount and final_amount. The difference teaches the template (see 9.7).
  • Undo removes the entry and its postings through TransactionNotifier.remove and returns the capture to the inbox; the capture row keeps the history. Approve is idempotent, so a double tap writes one entry.
  • Transfers between own accounts (a debit SMS from account A and a credit from account B with the same amount within 10 minutes) are offered as a single transfer, not as expense plus income.
  • Card bill payments (a bank debit to a card) are a liability payment, not spending, so totals aren't counted twice.

9.6 Cross-source dedupe

  1. Same reference and same direction → the same transaction. The key includes the direction so both legs of a transfer between own accounts survive — and are flagged as a transfer.
  2. A hand-typed entry with the same amount and direction within ±2 days → flagged as a likely duplicate and sent to review (entries auto-capture wrote don't count).
  3. The fingerprint blocks repeats in any status: a rejected capture is still the record that this alert was handled.
  4. Phase 4: source priority when merging with AA data: AA > SMS > email > notification > OCR.

9.7 Balance reconciliation and learning

  • Built: each alert's "Avl Bal" must follow from the previous alert's for the same account. It deliberately compares bank figures with bank figures — most people never enter an exact opening balance, so a check against Khazana's computed balance would flag everything. A break sends the capture to review. Planned: a "possibly missing transaction" banner with Find missing (AA fetch, Phase 4).
  • Planned: repeated user edits for the same template and field raise a local "template suspect" flag. With opt-in, an anonymous signal (template id and field only, no message text) helps us fix templates centrally.
  • Merchant aliases and categories learned from user choices reuse the existing merchant_alias table.

A valid session isn't enough for these. Each one needs a fresh biometric or PIN check on the device, signed with the device key.

14.4 What happens if something is stolen

If an attacker gets…Result
An access tokenUseless. Requests must be signed by the device's secure-chip key, which can't be copied. Expires in 15 minutes anyway.
A refresh tokenUseless for the same reason. Reuse detection also logs out that device's session.
A locked phoneData is encrypted under the vault PIN and keys sit in secure hardware. The user logs the phone out remotely from another device.
An unlocked phoneThe app still needs PIN or biometric. Sensitive actions need step-up. The device can be logged out remotely.
Our whole server databaseOnly ciphertext and metadata. No AA or credit plaintext is ever stored, and HSM-held keys can't be exported.
An insider with cloud accessSame as above, plus just-in-time access, two-person approval and recorded, write-once audit logs.
The user's password (phishing)There are no passwords. Passkeys can't be phished.
The user's SIM (SIM swap)Nothing. SMS OTP is never used for sign-in or recovery.
A tampered parser templateRejected. Templates are Ed25519-signed and version-pinned.
A fake bank SMSSender allow-list, balance-consistency check and unusual-amount rule send it to the Review inbox, not the ledger.
